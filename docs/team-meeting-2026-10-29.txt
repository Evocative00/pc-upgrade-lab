PC 업그레이드 실험실 — 팀 회의 요약 (2026-10-29)

회의 목표: 사용자가 “예산 안에서 무엇을 바꾸면 좋은지” 믿고 결정할 수 있게 만들기.
아래는 점검 결과와 개선 제안이며, 교수님의 정확한 요구사항은 별도 확인이 필요함.

1. 완료한 보안 수정
- Vite 8.3.0 → 8.3.3: Windows 개발 서버의 명령 주입 위험 수정.
- zod 4.6.5 → 4.6.7: 검증 중 메모리 고갈 위험 수정.
- 테스트 218개·lint·빌드 통과, 전체/배포 의존성 취약점 0건.
- UI 기능과 실제 DB는 이번에 변경하지 않았음.

2. 가장 중요한 발견
- 카탈로그 315종 중 과거 판매가 83종은 점검 당시 모두 만료 상태.
- 참고가 227종 중 219종은 유사 부품 기반 추정값이며 실제 판매가가 아님.
- 화면은 가격 종류·관측일을 숨겨, 가격은 보이는데 구매 합계에서 빠지는 혼동이 있음.
- 수집 도구는 있지만 정기 수집 → 검수 → 중앙 가격 게시가 자동으로 연결되지 않음.

3. 추천 작업 순서
① 가격 표시: 현재가/과거가/추정가, 확인 날짜, 출처, 합계 제외 이유 표시.
② 입력 보존: 메뉴 이동·부품 수정 후에도 구성과 예산·게임·해상도 유지.
③ 진단 안정화: 미반영 스캔 결과 보관·재반영, 같은 GPU의 성능과 VRAM으로 판정.
④ 가격 수집: 이용이 허용된 판매처 1곳·정확한 상품 20종으로 반복 수집 시범.
⑤ 구매 결정: 예산 내 실제 교체 후보와 추가 비용·호환 조건·판매처 링크 제시.
   구성 화면은 큰 소개·스캔 안내를 줄이고 부품 선택과 요약을 위로 배치.

4. 가격 수집·DB 개선 방향
- 흐름: 정확 SKU → 수집 → 상품/판매 단위 검증 → 관측 이력 → 승인 게시 → 화면.
- 기존 DB를 유지하고 수집 실행·실패 기록, 검수 대기, 판매처별 최신 상태를 추가.
- 배송비·재고·할인 조건을 구분하고 실패/품절/가격 없음/0원을 같은 값으로 처리하지 않기.
- RAM 묶음, CPU BOX/벌크, GPU 메모리·유통사 등 판매 구성이 다르면 별도 상품으로 검토.
- 오래된 네이버 쇼핑 검색 API는 2026-07-31 종료. 예전 튜토리얼을 그대로 쓰지 않기.
  공식 공지: https://developers.naver.com/notice/article/32530

5. 오늘 결정할 3가지
- UI·진단 오류 수정 담당과 데이터 수집 담당, 각 작업 순서·목표일.
- 수집 허용을 확인할 판매처와 시범 20개 상품, 수집 주기(제안: 하루 2회).
- 첫 추천 범위: 게임 1개 기준으로 예산 내 실제 교체 제품 선정까지 완성할지.

시범 완료 기준
- 잘못된 SKU 연결·중복 적재·입력 유실 0건, 만료 가격의 현재 합계 포함 0건.
- 수집 실패 이유·관측 시각·변경 이력 설명 가능. 7일 반복 운영으로 품질 측정.
- 고객이 “무엇을 유지하고 무엇을 왜 사야 하는지, 추가로 얼마가 드는지” 설명할 수 있음.
